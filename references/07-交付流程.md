# 07 交付流程：从开题到答辩

这份只管"什么时候交什么、什么算过了"。**具体的邮箱、命名规则、模板版本、截止日期在 `workflow/本地交付规格.md`**，那份是本地注入的，不在本文件里。

## 阶段与产物

| 阶段 | 主要产物 | 过这一步的判断标准 | 最常见返工原因 |
| --- | --- | --- | --- |
| 开题 | 开题报告、文献综述、阅读笔记、写作提纲 | 问题—方案—验证能对上；每篇引文能在原文找到 | 背景写了 5 个问题，正文只解决 2 个 |
| 需求分析 | 需求章（角色、用例、功能/非功能需求、追溯表） | 每条需求有验收条件，且能被后面章节接住 | 只有一张表，没有"为什么这么拆"的解释段 |
| 概要设计 | 架构、模块划分、数据模型、关键流程 | 每层职责清楚，模块边界不重叠 | 把需求复述一遍，没有设计决策 |
| 详细设计 | 按模块的实现、表结构、接口、异常处理 | 能看出"为什么这样设计"和"失败怎么办" | 写成代码注释的翻译 |
| 实现 | 可运行系统 + 部署说明 | 干净环境能跑起来 | 只在开发机跑通 |
| 测试 | 用例表、性能数据、结果分析 | 有异常路径；结果有归因 | 复述表格数字，不解释为什么 |
| 定稿 | 完整论文 + 查重 + 格式自检 | 编号连续、图表有引用、参考文献无孤条 | 删段落删出孤条引用 |
| 评阅 | 修改说明、修订稿 | 逐条回应，未改的说明理由 | 只写"已修改" |
| 答辩 | 讲稿、演示、问答准备 | 每个创新点能在 3 分钟内讲清 | 讲技术栈，不讲问题与取舍 |

## 交付前通用检查

1. **逻辑闭环**：背景里的每个问题，正文有对应设计，测试有对应用例。
2. **编号连续**：图、表、公式、参考文献编号不跳号；正文引用与实际编号一致。
3. **孤条**：删段落时检查它引的文献是否还有别处引用，没有就一并处理。
4. **术语一致**：同一概念全文只用一种叫法（首次出现给全称+缩写）。
5. **承诺兑现**："本文提出 A/B/C"必须能在目录里找到 A/B/C。
6. **格式**：按 `format/本地格式规格.md` 跑一遍（字体、字号、题注、页码）。

## 版本管理

- 旧版本**不覆盖**，另存新版本；文件名带版本号、日期、轮次（`vX.Y`、`R1/R2`）。
- 每轮改动留一份《修改说明》，写明"改了什么、为什么、还差什么"。
- 交付物与过程材料分开存：正式材料里不要混入内部检查报告、历史版本、脚本。

## 返稿处理流程（通用七步）

1. **导出**：把返稿的段落、批注、修订位置导成文本，先看清改了哪、批了哪。
2. **分类**：逐条批注归入——改文字 / 补内容 / 调结构 / 只提醒。**逻辑类批注不能靠删字解决。**
3. **判断差距**：每条按 `references/04-批注类型学.md` 判断"不及格 / 合格 / 优秀"，写清差在哪。
4. **改写**：按 `references/06-病灶清单与剂量.md` 的优先级（砍尾→去模糊→破对称→补证据→调节奏→换词）。
5. **生成**：以返稿为底稿生成新稿，保留批注锚点与修订痕迹（做法见 `references/08-docx修订与批注落地.md`）。
6. **自检**：文本与预期一致、批注锚点齐全、引用编号连续、格式符合本地规格。
7. **写修改说明 + 交付**：逐条对应 + 总量变化 + 仍待处理；发送方式按 `workflow/本地交付规格.md`。

## 修改说明怎么写

每条三句话：

```
改了什么：把（二）～（七）从 X 字压到 Y 字，删掉与方案无关的两段。
为什么这么改：按"场景问题→已有方案不足→本方案"重排，只保留能落地的内容。
还差什么：对照实验的指标口径还没定，第 7 章定稿后回补。
```

第三句不要省。它证明你知道差距在哪，而不是假装改完了。

## 常见错误

- 把"文字太多"当删字，删出逻辑断裂。
- 删掉某篇文献唯一的引用句，参考文献变孤条。
- 修订稿里把批注删了——老师看不到你回应了哪一条。
- 只在开发机跑通的系统，换环境启动失败。
- 修改说明写"已按要求修改"，没有逐条对应，等于没写。
