# 04 批注类型学：从导师的一句话到具体改法

导师批注通常很短，短到看起来像挑刺。但每一条背后是一个**明确的质量标准**。这份文件把它拆成八类，每类给：真实要求、差距判据、改法。

用法：拿到批注 → 先归类 → 再判断差距 → 再动手。**不要一看到批注就开始改字。**

---

## 拿到批注先问三个问题

1. **这条批注是在说"信息不对"还是"表达不对"？** 前者要补材料，后者才改文字。搞混了就会删了正确的内容。
2. **这条批注对应哪一章的哪一节？** 挂在某一段上的批注，问题常常不在那一段，而在它的上一段没有铺垫。
3. **老师用的是什么词？** 见下表，不同词指向不同严重程度。

| 老师的措辞 | 严重程度 | 通常指向 |
| --- | --- | --- |
| "可以再精简些" | 轻 | 表达冗余，删即可 |
| "不通顺" | 轻 | 句子层面，改语序 |
| "这里要想清楚" | 中 | 结构缺环 |
| "目的是什么" | 中 | 该节没有存在理由 |
| "这是 AI 的角度" | 重 | 语气越位，整段重写 |
| "缺少一段" | 重 | 逻辑链断裂 |
| "你的 X 体现在哪里" | 重 | 标题没被兑现，可能影响整体框架 |

---

## 类型 1：删冗余

**老师怎么说**
> 全文整体文字太多，可以再精简些。思考哪些是跟本课题相关的，哪些额外的信息——跟本课题不相关的，说了但是做不了的，冗余的信息。

**字面意思**：字太多。
**真实要求**：留下来的每一句，都必须能回答"它支撑我哪个设计或测试"。答不上就是冗余。

**差距判据**

| 档 | 表现 |
| --- | --- |
| 不及格 | 有整段内容与本课题无关（行业趋势、政策解读、通用技术科普） |
| 合格 | 每段都能指出它服务哪个章节 |
| 优秀 | 每段不仅服务，还在段末把这层关系说出来（"因此本课题不重复实现新的检索引擎"） |

**改法**
1. 给每段标一个"服务对象"（第几章哪个设计/测试）。标不出的，先标记待删。
2. 三类重点删：**不相关的**（行业宏观）、**说了但做不了的**（"未来可结合多模态"）、**重复的**（同一件事在背景、意义、创新点各说一遍）。
3. 删完检查：参考文献是否变孤条；某个概念的首次定义是否被删掉。

**陷阱**：老师说"文字太多"时，常常不是字多，是**同一句话被说了三遍**（背景说一次、意义说一次、创新点说一次）。这种删一遍就够了，不需要压缩句子。

---

## 类型 2：补逻辑环

**老师怎么说**
> 应该先明确现实中存在的场景（该场景中面临的问题必须是你后面要解决的），然后说出已有解决方案及其不足，这个不足是你后面要解决的。这是写作的一般逻辑。……你不能解决的问题不要写。

> 表述逻辑上缺少一段：LLM Wiki 是什么，有什么用？和 RAG 相比，在解决第一段中的问题时有什么好处？——只有 LLM Wiki 有好处，才有后续开展工作的必要。

**字面意思**：少了一段。
**真实要求**：**问题—方案—验证必须一一对应**。写进"问题"清单的每一条，后面都要有一个设计接住、一个测试验证。

**差距判据**

| 档 | 表现 |
| --- | --- |
| 不及格 | 背景提了 5 个问题，正文只解决 2 个；或者正文做了 A，背景里根本没提 A |
| 合格 | 问题清单与章节一一对应 |
| 优秀 | 每个问题都能指出"别人怎么解决的 → 缺什么 → 我怎么补 → 在哪验证" |

**改法**
1. 列**问题银行**：把背景里提到的每个问题编号 P1…Pn。
2. 在每章开头标注它解决哪几个 P。
3. 有 P 没有章 → 删 P 或加章；有章没有 P → 补背景。
4. 概念缺环（"什么是 LLM Wiki"）：补一段三句话的定义段——**是什么 → 和已有方案（RAG）怎么不同 → 在解决本文问题上多出什么好处**。第三句最关键，缺了读者不知道为什么要有这个东西。

---

## 类型 3：兑现标题

**老师怎么说**
> 注意思考：除了 LLM Wiki 以外，本论文的标题是管理系统。那么论文工作如何体现出【管理平台】？

**字面意思**：标题里的词没写出来。
**真实要求**：**标题里每个实词都要有对应的章节、功能、界面和测试**。

**差距判据**

| 档 | 表现 |
| --- | --- |
| 不及格 | 标题是"管理平台"，正文全是算法；或标签是"智能"，只做了关键词检索 |
| 合格 | 标题每个词都有一个专章或专节 |
| 优秀 | 标题每个词都有一个可演示的功能 + 一条测试用例 |

**改法**
1. 拆标题成词："基于 LLM Wiki 的 / 文档知识库 / 管理平台"。
2. 每个词问一句：**它在论文的第几章被做出来了？** 答不上就补。
3. "管理平台"至少要落到：多用户/角色、知识库的增删改、内容生命周期（草稿—审核—发布—归档）、权限、审计。只有"能问答"不叫平台，叫问答系统。

---

## 类型 4：明确小节目的

**老师怎么说**
> 分析【领域知识库系统】的目的是什么？证明技术思路？还是用作于 LLM Wiki 的对比？还是发现技术不足？

**字面意思**：不知道这节想干嘛。
**真实要求**：每一节开始前，作者要能一句话说出它的功能：**证明 / 对比 / 发现不足 / 定义**。四者必居其一。

**差距判据**

| 档 | 表现 |
| --- | --- |
| 不及格 | 整节读完不知道结论是什么，像资料汇编 |
| 合格 | 节末有一句"这条线的结论是……" |
| 优秀 | 节首就声明目的，节末的结论直接变成下一节的任务 |

**改法**
1. 给每节写一句"本节目的"（不出现在正文里，写在旁边）。
2. 目的相同的两节合并；没有目的的节删。
3. 节末加一句收束，句式：`这条线的结论是……`（谢巨龙、赵翔都这么写）。

---

## 类型 5：语气角度（最难改）

**老师怎么说**
> 显然这是大模型的语气。
> 说这句话的语气不对。这是 AI 的角度，不是你的角度。
> AI 角度。
> 这句话就很多余。谁都知道不能宣称。

**字面意思**：语气不像学生写的。
**真实要求**：论文里只写**"我做了什么、为什么这么做、怎么验证的"**，不写"我打算怎么写""我知道不能宣称什么""需要注意什么"。

**五类"AI 角度"，逐条对号入座**

| 类别 | 长什么样 | 为什么错 | 怎么改 |
| --- | --- | --- | --- |
| 写作计划 | 「正文目标约 2.4 万字」「按模板八章撰写」 | 这是开题报告的话，论文只说结果 | 删 |
| 防御性声明 | 「本课题不宣称首次提出 LLM Wiki」 | 谁都知道不能宣称，写出来反而像心虚 | 删，直接写你做了什么 |
| 元话语 | 「需要注意的是」「值得一提的是」「综上所述，本节……」 | 读者不需要被提醒 | 删 |
| 引用不存在的材料 | 「见《内部设计草案》」（正式材料里没有） | 读者查不到 | 删或改成正文中直接说明 |
| 解释显而易见的事 | 「管理系统需要有用户」 | 浪费篇幅 | 删 |

**差距判据**

| 档 | 表现 |
| --- | --- |
| 不及格 | 出现上述任意一类，且是成段出现 |
| 合格 | 零星出现，删掉不影响 |
| 优秀 | 全篇只有"本文/本系统"承担责任，没有一句在讲"我打算" |

**改法**
- 全文搜这几个词：`需要指出` `值得注意的是` `综上` `旨在` `拟` `计划` `不宣称` `目标约`。
- 每个"本课题"问一句：这是**动作**还是**声明**？声明删掉，动作保留。
- 主语问题：作者出场那句要短（"为此，本文设计了…"），不要写成"本文针对上述复杂问题提出了一种综合性的、具备自适应能力的框架"。

---

## 类型 6：精简表达

**老师怎么说**
> 可以再精简些：直接说本课题做哪些内容。
> 这部分不要这样写，直接写做到什么程度。

**字面意思**：绕了。
**真实要求**：**结论先行**。删掉铺垫、动机复述、过渡句。

**改法**
1. 把每段第一句和最后一句抽出来读。如果首句是铺垫、末句才是结论——**调换顺序**。
2. 删掉三类铺垫：`为了……` 开头的动机句（上一段已经说过）、`正如前面所述`、`在此基础上，我们进一步……`。
3. "分期/阶段/里程碑"改成"做到什么程度"：不写"第一阶段…第二阶段…"，写"首期实现 A/B/C，本期不实现 D"。

---

## 类型 7：语句不通

**老师怎么说**
> 不通顺。

**真实要求**：通常是三种病——主谓隔太远、并列项不齐、一个句子承担了两件事。

**改法**
1. 找主干：把定语全删，看主语和谓语能不能连上。
2. 并列项词性要一致（都是名词或都是动宾）。
3. 一句只干一件事；两件事就拆成两句，但拆完要保证**长句仍然存在**（见 `01-指纹与诊断.md`）。
4. 超过 150 字必拆。

---

## 类型 8：格式细节（不是写作问题）

**老师怎么说**
> 注意：开题报告和后面论文中，双引号要使用宋体。这是直接使用大模型输出的一个问题。

**真实要求**：技术性检查，不用改内容。**但这句话透露了一个信息**：老师会注意到"哪些痕迹说明你直接用了大模型"。同源问题还有：英文直引号 `"` 混入中文、全角半角混排、Markdown 语法残留（`**`、`#`）、表格用制表符对齐。

**改法**：交稿前跑一遍格式检查（见 `bishe-thesis` 的 `check_docx.py`）。

---

## 类型 9：加分项提示（这是老师给的机会）

**老师怎么说**
> 这个地方要想做好需要仔细琢磨一下。做好了论文容易得高分。

**真实要求**：老师在告诉你哪一块是评阅的区分点。通常是：**对照实验**、**失败案例分析**、**系统与算法的分工**。

**改法**（以对照实验为例）
1. 固定变量：同一批语料、同一组问题、同一模型、同一硬件。
2. 基线要具名：不是"现有方法"，是"常规 RAG（固定分块 512、Embedding 模型 X、top-k=5）"。
3. 指标要定义：准确率怎么算、由谁判定、人工还是模型裁判。
4. 报告不利结果：哪一项没赢，为什么。
5. 写清结论边界："在 20—30 篇文档、50—100 个问题上"。

---

## 回复批注的写法

每条回复三句话，**不要写"已修改"**：

```
改了什么：把（二）～（七）从 X 字压到 Y 字，删掉了与方案无关的两段（政策解读、通用技术科普）。
为什么这么改：按"场景问题→已有方案不足→本方案"重排，只保留能在第 4—7 章落地的内容。
还差什么：对照实验的具体指标口径还没定，等第 7 章定稿后回补。
```

第三句很重要：它证明你知道自己离"优秀"还有多远，而不是假装改完了。

## 一张总表

| 类型 | 老师关键词 | 一句话真实要求 | 改法核心 |
| --- | --- | --- | --- |
| 删冗余 | 文字太多、精简 | 每句都要服务某个设计或测试 | 标服务对象，删不相关/做不到/重复 |
| 补逻辑环 | 缺少一段、逻辑 | 问题-方案-验证一一对应 | 建问题银行，逐条映射章节 |
| 兑现标题 | 你的 X 体现在哪 | 标题每个实词都要落地 | 拆词，逐词找章节和测试 |
| 明确目的 | 目的是什么 | 每节只能是证明/对比/发现不足/定义 | 写"本节目的"，节末收束 |
| 语气角度 | AI 角度、大模型语气 | 只写做了什么，不写打算和声明 | 搜元话语词，删声明保动作 |
| 精简表达 | 直接说 | 结论先行 | 首末句调换，删铺垫 |
| 语句不通 | 不通顺 | 主谓连得上，一句一件事 | 抽主干，查并列，150 字必拆 |
| 格式细节 | 引号、字体 | 技术检查 | 跑格式脚本 |
| 加分项 | 容易得高分 | 老师在指区分点 | 对照实验/失败分析做扎实 |
