# 02 章节骨架

每节给：段落配方 + 必写 + 不写 + 一个真实样本的长度与结构。

---

## 摘要（800–1000 字，4–5 块）

**配方**（最常见，6/19 篇）：

```
① 背景 + 三重挑战（150–200 字，挑战数量 = 后面工作数量）
② 一句总述本文做了什么（50–80 字）
③ 工作 1、2、3（每块 150–300 字）
④ 效果（100–200 字，带数字）
```

**写法**：

- 首句多数是"随着…"（9/19），但**首选是给定义或判断**（6/19）：给出定义，第二段立刻"然而"。因为"随着"式首句可以互换，把一篇的首句搬到另一篇毫无违和。
- 挑战用编号，"一是…；二是…；三是…"，**挑战数必须等于工作数**。
- 每块工作的三拍：`针对 X 问题，本文提出/设计并实现 Y。该方法通过 A…，通过 B…，实现 C。实验/应用表明…`
- 效果句必须有：数据集/规模 + 基线 + 指标 + 数值。

**必写**：挑战 → 工作 → 效果。
**不写**：代码/伪代码/函数名/超参数；公式和长定义（术语给一句 20–30 字的解释就够）；文献综述（把"深入研究分析了…梳理了…"当工作项是反例）；致谢口吻与谦辞；"如图 1""见表 2""第 3 章"这类指引；未来展望。

**长度**：学位论文 800–950，期刊 400–540。单句 ≤150 字，均句 70–80。

---

## 第 1 章 绪论

### 1.1 研究背景与意义（600–900 字）

五步：

1. **场景**：谁、在什么情况下、做什么事。
2. **该场景的具体问题**（必须是你后面要解决的）。
3. **已有方案及其不足**（不足必须由你的方案补齐）。
4. **本文切入**。
5. **意义**：分理论意义/实践意义，各 2–3 句。

导师原话（真实批注）："应该先明确现实中存在的场景（该场景中面临的问题必须是你后面要解决的），然后说出已有解决方案及其不足，这个不足是你后面要解决的。这是写作的一般逻辑。"

**不写**：与本课题无关的行业趋势；说了但做不了的内容；你能描述但解决不了的问题。

### 1.2 国内外研究现状（1200–2000 字）

按方向分 3 小节（不按时间堆）：

```
1.2.1 方向 A
1.2.2 方向 B
1.2.3 方向 C（= 本文的直接前身）
```

每小节内部按时间线走，每句一个作者一个贡献：

> 1986 年，Lesk 等人针对词义歧义问题，提出了一种消除字典语义歧义的方法，利用词典中的定义和示例确定单词的正确语义。

**这类句子必然长**（60–90 字），因为塞了年份、人名、问题、方法、机制五样东西。

每小节结尾必须是**缺口句**：

> 尽管 n-gram 模型在捕捉局部结构方面表现出一定的有效性，但它们在处理长距离依赖时具有一定难度。

**用文献的方式**：文献句以 `[12]` 结尾，自家句以"本文/结果表明"开头，**不能混**。写"研究表明，本文提出的方法…"会让读者分不清是谁做的。

**不写**：与本课题无关的综述；把"我参考了哪些技术"写成"研究现状"；大段复制别人的定义。

### 1.3 研究内容

用编号列，每条一句主体 + 一句方法：

> （1）文档接入与解析。首版接收 PDF、DOCX 和 Markdown，解析结果保留页码、标题层级、表格与图片位置……
> （2）……

**必写**：每条都能在第 4–7 章找到对应章节。
**不写**：把计划、阶段、里程碑写进来（那是开题报告的事）。

### 1.4 论文组织结构

固定句式，一章一句，动词不重复（介绍/阐述/设计/实现/验证/总结）：

> 第一章是绪论，……。第二章是相关技术，……。第三章……。

这段是全文唯一允许的"目录复述"，导师靠它判断结构是否成立。

## 第 3 章 需求分析（或"需求分析与概要设计"）

### 章首导语（3–4 句）

> 本章内容为……。首先……；随后……；接着……；最后……。

**这四句是承诺，后面对应四节，顺序和名词都对得上。**

### 3.1 需求来源与调研结论

一张对比表（对象/做法/可借鉴/未解决的需求）+ 两段结论。

结论段必须写**边界**：

> 调研结果说明两项边界。RAG、GraphRAG 和摘要树已经解决"如何找到相关内容"，因此本课题不重复实现新的检索引擎。……需要补齐的是……

### 3.2 用户角色与典型场景

角色表 + **一段典型场景的白描**（谁在什么情况下做什么，遇到什么，系统怎么响应）。

### 3.3 系统用例

用例图 + 每个用例一句话 + 用例之间的关系（包含/扩展）。

### 3.4 功能需求 ← 最关键

**写法：一张表当索引 + 每类需求一段解释。**

每段五拍：

1. **功能名 + 为什么需要**
2. **系统应具备什么**
3. **具体怎么做**
4. **边界/例外**
5. **落到用例图/需求编号**

真实样本（蒋明君）：

> （2）教材文档知识库管理功能需求
> 对教材文档、教材知识库、教材知识图谱的管理功能，是智慧教材应用平台的核心功能之一。系统将同一课程下所属的教材和相关教学资料归属为知识库，教师可以根据教学需要灵活地创建、删除知识库……系统支持上传不同格式的教材，并对教材文档进行解析，上传后的文档支持查看和删除。

注意：没有一句是"该模块实现 X、Y、Z 三项功能"。

**不写**：实现细节（重试策略、错误码、事务边界）——那是第 5 章的事。这里只说"系统要能做什么、做到什么程度"。

### 3.5 非功能需求

按类别分（性能/可靠性/安全/可维护/可部署），每条给**验收方法**而不只是指标：

> 单机、16 GB 内存环境下，检索接口 P95 不超过 1.5 s。验收：使用 24 篇固定语料和脚本重复请求，记录 P50、P95、P99。

### 3.6 需求优先级与系统边界

首期做什么、本期不做什么、为什么不做。

**必写**："本期不实现 X"要有理由，且不能是"时间不够"。

### 3.7（可选）需求追溯

需求 → 设计模块 → 接口/数据对象 → 测试编号。这张表是给评阅老师看的，证明你的需求没有掉在地上。

### 本章小结（4 句）

`做了什么 → 用了什么 → 得到什么 → 给下一章留什么钩子`。**不写自我评价。**

---

## 第 4 章 概要设计

- **4.x.1 总体架构**：分层（表示层/应用层/领域层/基础设施层），每层一段：这一层负责什么、不负责什么、依赖谁。
- **4.x.2 技术选型**：每个选型一句话理由（为什么不用另一个），**不要罗列技术栈清单**。
- **4.x.3 模块划分**：模块表 + 模块之间的调用关系。
- **4.x.4 数据模型**：E-R 图 + 关键表说明（不必逐字段）。
- **4.x.5 关键流程**：时序图/流程图 + 一段文字解释为什么这样排。

**不写**：详细到接口参数的实现（留第 5 章）；把需求复述一遍。

---

## 第 5 章 详细设计与实现

按模块分节：`5.1 xx 模块设计与实现`。

每个模块三件：**设计约束 → 类/表/接口 → 关键实现与异常处理**。

写法上最容易犯的错是写成代码注释的翻译。救回来靠两句话：

- 为什么这样设计（放弃了什么方案）
- 出了什么问题怎么处理（失败路径）

> 任务进入队列时先保存文档版本和任务记录，再启动解析与模型调用；解析失败、模型超时和结构校验失败使用不同错误码。

---

## 第 6 章 测试

- 测试环境：**具体到型号**（CPU/内存/硬盘/网络延迟/浏览器版本）。
- 功能测试：表格（用例编号/输入/预期/实际/结论），每条给**正常路径 + 异常路径**。
- 性能测试：指标 + 方法 + 数据 + 对比基线。
- 结果分析：**不要复述表格数字**，要解释"为什么是这个结果"。

真实写法（何一苇）：

> 1.2 秒，失败率为 0，原因是系统的本地预处理、缓存机制和硬件加速，缩短了响应时间……知识更新平均耗时只有 10 分钟，原因是该系统采用增量更新策略实现高效同步。

格式是：`数字 + 归因`，连用两三次后换成"主要因"，避免句式重复。

---

## 第 7 章 总结与展望

**7.1 总结**：不要复制摘要。按"问题→方案→验证→结论"四段写，比摘要多写"为什么这样做"。

**7.2 展望**：3–4 条，每条必须是**你论文里真实存在的边界**，不是"未来可以结合多模态"这种通用话。

好样本：

> 局限性：LLM 对专业术语有理解偏差，需人工校验；质量保障需安全专家介入关键审核；未验证核电、火电泛化能力。

差距句写在最后，写成"下一步任务"：

> 后续仍需围绕权限约束、知识时效控制与复杂场景适配作进一步细化。

---

## 本章小结（通用公式）

> 本章对……进行……，利用……从……中抽取……，结合……提高质量。通过……实现……，确保……。最终，……存储在……，利用……实现……，为后续……提供……支持。

四件事：做了什么 → 用了什么 → 得到什么 → 给下一章留什么钩子。最后半句"为后续…提供…支持"是钩子，不是客套。
