# 改前改后：三个真实案例

每个案例给：改前、改后、体检数字、改了什么、为什么这么改。
案例来自作者本人的真实初稿，已去掉具体课题词；数字保留，方便你对照自己的稿子。

---

## 案例 1：一句话装不下"条件 + 机制 + 结果"

### 改前（81 字，4 句）

> 数据接入和加工需要保持任务可恢复。任务进入队列后，系统先保存数据集版本和任务记录，再启动解析与模型调用；HTTP 请求不等待完整加工结束。解析失败、模型超时和结构校验失败使用不同错误码。操作者重试时从失败阶段继续。

### 改后（一段，2 句长 + 1 句短）

> 数据接入与加工是一条可能中断的长链路，因此系统把"数据集版本—加工任务—阶段产物"三者分开保存：任务进入队列时先落库数据集版本和任务记录，再启动解析与模型调用，HTTP 请求在任务入队后即返回，不等待整条链路结束。解析失败、模型超时和结构校验失败分别返回 E-PARSE、E-TIMEOUT 与 E-SCHEMA 三类错误码，操作者在任务详情页看到的是"哪一阶段失败、失败原因、能否重试"，而不是统一的"加工失败"。重试从失败阶段继续。

### 数字

| 指标 | 改前 | 改后 | 学位论文参考 |
| --- | --- | --- | --- |
| 平均句长 | 30.3 | **52.1** | 52.8 |
| 长句占比 | 8.7% | **62.5%** | 40.6% |
| 句长 CV | 0.45 | **0.60** | 0.70 |
| 相邻句长差 | 18.0 | **40.6** | 30.4 |

### 改了什么

| 动作 | 改前 | 改后 |
| --- | --- | --- |
| 首句给因果，不给结论 | "需要保持任务可恢复" | "是可能中断的长链路，因此系统把……三者分开保存" |
| 长句装三样东西 | 两句短句各说一半 | 一句 108 字：条件（入队时）+ 机制（先落库再启动）+ 结果（请求即返回） |
| 具体化 | "不同错误码" | "E-PARSE、E-TIMEOUT、E-SCHEMA 三类" |
| 短句收束 | 无 | "重试从失败阶段继续。"（11 字） |
| 去掉不实内容 | "不重复计费"（系统没有计费模块） | "不重复写入结果表" |

**信息量没变，只是把"条件+机制+结果"合进了一句。** 这就是"人味"最可操作的部分。

## 案例 2：结果句没有证据

### 改前

> 实验结果表明，该系统在客服问答任务中表现出色，显著提高了知识库的应答能力。

问题：无数据集、无基线、无指标、无数值。"表现出色""显著提高"都是修辞。

### 改后

> 实验结果表明，在电信客服的 1200 条测试问句上，与 BM25 基线相比，本系统的召回率从 0.61 提升到 0.78，答案可用率从 0.55 提升到 0.71。

### 改了什么

- 补**规模**：1200 条测试问句
- 补**基线**：BM25（具名，不是"现有方法"）
- 补**指标**：召回率、答案可用率
- 补**数值**：0.61→0.78、0.55→0.71
- 删掉"表现出色""显著"

**如果确实没测**：改成"该功能在用例 T-QA-03 中验证了可用性，性能指标待第 7 章补充"。不要用形容词假装测过。

## 案例 3：三元并列顶替论证

### 改前

> 页面、文本块和实体关系并存的检索入口。

问题：三项并列，读者看到的是清单，看不到主次和关系。

### 改后

> 检索入口有三个，优先级不同：页面优先，页面证据不足时回退到文本块，实体关系只用于扩展相关概念。

### 改了什么

- 「A、B、C」改成「主项 + 次项 + 限定项」
- 用句子说关系（优先 / 回退 / 只用于）
- 读者一眼能看出什么时候用哪个

**判据**：全文"A、B、C"式三项串联超过 4.5 处/千字，说明你在用枚举代替论证。

---

## 三个案例的共同点

| | 改前 | 改后 |
| --- | --- | --- |
| 信息 | 只有主张 | 主张 + 条件 + 数值 + 边界 |
| 句子 | 长度均匀 | 长句撑机制，短句收束 |
| 责任 | 主语模糊（"系统""表现出色"） | 谁、在什么条件下、做了什么 |

**没有一条是靠换同义词做到的。** 换词是最后一步，前三步是补内容。
